# Серверная админка Ѣ

Готовая админка Django: `/admin/`. На GitHub Pages выполняется только статическая страница с объяснением; пароль и запись в базу работают после запуска серверной части. В коде нет встроенного или общего пароля.

## Запуск на личном хосте

Нужны сервер с Docker Compose, домен с A-записью на сервер и открытые 80/443. Клонируйте весь репозиторий. Все команды ниже выполняются из его корня.

1. Скопируйте `server/.env.example` в `.env`. Укажите домен без https. Для DJANGO_SECRET_KEY и POSTGRES_PASSWORD сгенерируйте ДВЕ отдельные строки командой `python3 -c 'import secrets; print(secrets.token_urlsafe(48))'`. Не публикуйте `.env`.
2. `docker compose up -d db`
3. `docker compose build web`
4. `docker compose run --rm web python manage.py migrate`
5. `docker compose run --rm web python manage.py import_site`
6. `docker compose run --rm web python manage.py collectstatic --noinput`
7. `docker compose run --rm web python manage.py init_admin --username admin`
8. Сохраните пароль. Можно ввести свой скрыто либо нажать Enter: команда сгенерирует и покажет случайный пароль один раз. В базе хранится только хеш.
9. `docker compose up -d`
10. Откройте `https://ВАШ-ДОМЕН/admin/`.

Команда import_site переносит текущие базы карточек, ударений, пунктуации и пробников, включая пояснения. Повторный запуск добавляет отсутствующие исходники и сохраняет изменения администратора. PDF серверу не нужны.

## Работа с материалами

- «Карточки»: выбрать номер, вид карточки, заполнить слово/контекст и кнопки. Каждая кнопка вводится с новой строки. Для буквы указать части до/после пропуска и правильную букву. Для ударения слово строчными, части до/после ударной гласной и саму гласную. Для пунктуации каждую часть предложения ввести с новой строки; позиции кнопок считать от 0.
- «Задания пробников»: полный текст, условие, источник, тип проверки и правильные ответы (каждый допустимый ответ с новой строки).
- У заданий одного текста укажите одинаковую «Группу общего текста». Для совместной генерации 1–3 и 23–26 нужен полный комплект выбранных номеров для этой группы.
- Общее правило можно выбрать из списка, свое пояснение имеет приоритет.
- До готовности снимите «Опубликовано». После сохранения опубликованный материал попадёт на сайт при обновлении страницы. Незаполненное пояснение и неправильный набор кнопок не позволят опубликовать новый материал.
- ID не вводится: база выдает следующий уникальный номер в одной последовательности для карточек и пробников. Правки ID не меняют. Существующие видимые ID пробников сохраняются. Снятие с публикации не освобождает номер. На карточках ID скрыт.
- «Номера заданий»: номер ЕГЭ, название, баллы. Предлагается следующий номер; можно выбрать пропущенный. Дубликат запрещен. Новый номер появляется в меню карточек после добавления опубликованных карточек, в выборе пробника — после создания задания.
- Пароль: `docker compose run --rm web python manage.py changepassword admin`.

База пользователей и материалы в PostgreSQL, том `database`. HTTPS выдаёт Caddy. Статические файлы админки — том `appdata`. Резервируйте PostgreSQL отдельно от репозитория: `docker compose exec -T db pg_dump -U ege ege > backup.sql`; храните копию на другом устройстве. Восстановление в пустую базу: `docker compose exec -T db psql -U ege ege < backup.sql`. Перед обновлением делайте бэкап. Код из GitHub не содержит созданных в админке материалов: они хранятся в БД, их переносит резервная копия.

## Проверки

`python manage.py test content` — вход/права, CSRF, создание и редактирование, снятие с публикации, проверка кнопок и добавление номера.

`python manage.py check --deploy` — проверить настройки развертывания.

Для локальной разработки установите requirements.txt, задайте случайный DJANGO_SECRET_KEY, DJANGO_DEBUG=1. Затем migrate, import_site, init_admin, runserver. При отсутствии POSTGRES_DB используется локальная SQLite в server/data; это только локальная разработка. При DEBUG=1 админские static отдает runserver. Не включайте DEBUG в интернете.

## Защита сервера и обновление

Схема: Caddy (HTTPS) → Nginx (статические файлы, ограничения запросов) → Django (только админка и content.js). База, Django и Nginx не публикуют порты на хосте. Не добавляйте им `ports` и не открывайте Gunicorn напрямую: Django доверяет HTTPS-заголовку внутреннего шлюза.

Nginx доверяет IP клиента только от контейнера Caddy с адресом `172.30.74.2`. Подсеть `172.30.74.0/24` должна быть свободна; при её смене измените также `set_real_ip_from` в `server/nginx.conf`. При подключении внешнего CDN настройте доверенные адреса CDN в Caddy по документации провайдера, иначе лимиты будут считать IP CDN вместо посетителя. Никогда не доверяйте произвольному `X-Forwarded-For` из интернета.

Лимиты: сайт — 20 запросов/с на IP с кратким всплеском до 100; вход в админку — 5 запросов/мин с всплеском до 5 (включая GET); content.js — 2 запроса/с со всплеском до 20; одновременно до 128 запросов на IP и 256 на сервер. Превышение возвращает 429. Это стартовые значения: проверьте при реальной одновременной работе класса, прежде чем использовать в школе. Размер тела запроса — до 1 MiB; настроены тайм-ауты. Эти меры ограничивают HTTP-перегрузку и перебор с одного IP, но не распределённый подбор и не сетевой DDoS. Для последнего нужен хостинг с фильтрацией трафика до сервера. Админку желательно ограничить VPN или списком доверенных IP на шлюзе, когда будут известны нужные адреса.

Перед обновлением сделайте отдельный бэкап PostgreSQL, сохраните его вне сервера и проверьте восстановление. Имена томов `database`, `appdata`, `certificates`, `caddyconfig` и каталоги данных сохранены. Обновление: `docker compose build web gateway`, `docker compose run --rm web python manage.py migrate`, `docker compose run --rm web python manage.py collectstatic --noinput`, затем `docker compose up -d --remove-orphans`. Не используйте `down -v`: это удалит данные. Изменённые публичные материалы из файлов требуют пересборки gateway; изменения из админки доступны через content.js без пересборки.

Лимиты памяти контейнеров суммарно около 1.25 GiB без ОС и сборки: для этой конфигурации разумно от 2 GiB RAM, с наблюдением за расходом. На маленьком VPS возможны OOM и перезапуски. Ограничена ротация Docker-логов, но свободное место БД, сертификатов и резервных копий нужно контролировать отдельно. Запланируйте `clearsessions` и регулярные бэкапы средствами сервера.

Полная проверка конфигураций контейнеров запускается в GitHub Actions. Локально дополнительно выполните `docker compose config --quiet` и проверки из workflow перед публикацией. `check --deploy` намеренно предупреждает об отключённых HSTS preload/includeSubDomains: их нельзя включать, пока не проверен HTTPS всех поддоменов. На самом сайте HSTS первоначально установлен на 1 час.

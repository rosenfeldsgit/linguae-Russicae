# Вход для нового чата Codex

## Контекст

Репозиторий `rosenfeldsgit/linguae-Russicae`, действующий сайт `https://rosenfeldsgit.github.io/linguae-Russicae/`. Ветка подготовки — `docs/knowledge-base`; после слияния читать `main`. Пользователь попросил подготовить базу, а оформление отдельного раздела передаёт следующему чату.

## Цель следующего этапа

На основании этих файлов реализовать самостоятельный раздел «Теория» с доступом из общего интерфейса сайта. Прочитать корневой `AGENTS.md`, `knowledge-base/README.md`, `CURRENT_STATE.md`, `chapter-index.json`, `sources.json`, затем главы. Не считать, что в памяти чата уже известны прошлые договорённости.

## Содержание и ограничения

1. Канонический материал — Markdown в `chapters/`, не старые эвристические строки из `explanations.js`.
2. Сохранять различия частей речи, смысловые условия, исключения и опровержения ложных упрощений. Не превращать «обычно» в «всегда».
3. Не присваивать сложному географическому названию статус исключения, если есть правило. Не объявлять все слова на -мый несуществующими без НЕ. Не подменять краткое прилагательное кратким причастием.
4. Не выдавать снимок словника проекта за полный официальный список нового года. Показывать происхождение словников и дату проверки.
5. Главы №6 и №7 — дополнительные; теория шире пока имеющегося числа карточек. Номера 2, 3, 8, 23–27 не показывать как готовые статьи.
6. Существующие ответы, варианты, тексты тренировок и алгоритм ротации не менять попутно.

## Предлагаемая реализация

- Маршрут `/theory/` со списком тем, поиском и открытием отдельной главы. Для GitHub Pages учитывать базовый путь `/linguae-Russicae/` и возможность прямого открытия URL.
- Правила, примеры, исключения и разборы должны визуально различаться, но оставаться одной читаемой статьёй. На телефоне — один основной столбец, без переполнения широкими таблицами.
- Каждому правилу дать якорь по его ID, например `R13-04`. Ссылки из будущих карточек могут вести на такое правило. Не подбирать ruleId по вхождению трёх букв в слове; связывать по проверенному смыслу и морфологии.
- Исходные ID в Markdown не обязаны отображаться ученику. Это внутренние устойчивые идентификаторы.
- Первичные источники и дата проверки доступны в конце главы; вспомогательные материалы отмечены отдельно.
- Возврат из теории должен сохранять разумный путь назад к текущей тренировке. Не сбрасывать её через случайную глобальную инициализацию скриптов приложения.
- Сборку выполнить `node knowledge-base/tools/build.cjs <output-dir>`. `chapters.json` содержит главы целиком; `rules.json` — правила отдельно. Оба файла генерируются из одного источника.
- При рендеринге Markdown не исполнять HTML/JavaScript из текстовых данных; использовать безопасный разрешённый набор элементов.

Это предложение структуры, а не уже согласованный макет. Сохранять текущие шрифты, цвета и подход к интерфейсу. Если начнётся новая дизайнерская работа, учитывать пользовательские требования к референсам Pinterest и напомнить о выборе последней доступной модели Astra.

## Проверки перед PR

1. Сделать отдельную резервную ветку от актуального main.
2. Проверить источник официального формата экзамена на дату публикации.
3. Сборка базы и проверка всех локальных ссылок.
4. Загрузка `/theory/` и прямой главы в GitHub Pages с проектным префиксом; мобильная ширина и длинные таблицы.
5. Страница работает при перезагрузке и возврате к тренировке. Старые тренировки, пробники и история не сломаны.
6. Если добавлены публичные файлы, обновить `PUBLIC_FILES` в `server/content/views.py`: из него собирается публичный артефакт.
7. Запустить подходящие существующие проверки. Доставить изменения PR; не обходить защиту основной ветки.
